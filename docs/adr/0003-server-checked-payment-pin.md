# 0003. 서버에서 확인하는 결제 비밀번호와 5회 실패 잠금

- 상태: 승인됨
- 날짜: 2026-11-21

## 배경

로그인 세션이 살아 있는 기기를 다른 사람이 집으면, Privy 임베디드 지갑은 추가 확인 없이 서명할 수 있다. 출금과 Aave 넣기·빼기 같은 자산 이동 전에 한 번 더 확인하는 단계가 필요하다. 이 확인 단계는 서명 키를 보관하거나 나눠 갖지 않아야 한다(비수탁).

## 결정

- 6자리 결제 비밀번호를 서버에 scrypt 해시로만 저장한다(`lib/payment-pin/hash.ts`, Supabase `payment_pins`).
- 출금(`withdraw`), 넣기(`supply`), 빼기(`redeem`) 전에 `/api/payment-pin/verify`로 확인하고, 해당 작업 한 번에만 쓸 수 있는 60초짜리 승인(grant)을 받아 `/consume`으로 소비한다.
- 5회 틀리면 잠근다. 잠금은 시간이 지나도 풀리지 않고(`LOCK_UNTIL` 9999년) 복구 절차로만 해제한다.
- 잠긴 동안에는 서버가 비밀번호 사용 끄기 요청을 `423`으로 거부하고, 화면은 넣기·빼기·출금 버튼과 사용 토글을 비활성화한다.
- 복구는 두 방법이다. 이메일 계정은 Privy 이메일 인증 코드로, 지갑 계정은 서버가 발급한 문구에 대한 지갑 서명으로 본인을 확인한다. 복구 토큰은 10분 동안 유효하다.

## 검토한 대안

- **Privy MFA 또는 키 쿼럼**: 서명 단계에서 강제되므로 더 강하지만 Privy 설정과 사용자 흐름이 복잡해진다.
- **기기 생체 인증(WebAuthn) 확인**: 사용성은 좋지만 기기를 바꾸면 다시 등록해야 하고 웹 환경마다 지원이 다르다.
- **시간 경과 후 자동 잠금 해제**: 사용자 불편은 줄지만 시간을 두고 계속 추측하는 공격을 막지 못한다.

## 결과

- 장점: 서버는 비밀번호 해시와 짧은 승인만 다루고, 키에는 관여하지 않는다.
- 한계: 이 확인은 **앱 화면과 서버 API 수준의 잠금**이다. 서명은 여전히 Privy 지갑에서 이루어지므로, 앱을 거치지 않고 지갑에 직접 접근하는 경로는 막지 못한다. 보고서와 사용자 안내에서 "추가 확인 단계"로 설명하고 "키 보호"로 설명하지 않는다.
- 단점: Supabase가 멈추면 비밀번호를 켠 사용자는 넣기·빼기·출금을 할 수 없다.
- 단점: 잠금 해제가 복구로만 가능해서, 이메일이나 연결 지갑에 접근할 수 없는 사용자는 지원팀 개입이 필요하다.
